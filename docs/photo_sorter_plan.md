## 0. 한 장 요약

| 항목 | 결정 |
|---|---|
| 작업 방식 | 사진은 모두 REJECT 상태로 시작. `→` 다음, `←` 이전, `Space` GOOD 지정/해제(토글). GOOD 사진에는 초록 테두리와 `GOOD` 표시가 계속 붙어 있음 |
| 저장 위치 | 시작 화면에서 **사진 폴더 + 결과 저장 위치를 둘 다 지정해야 시작 가능**. 저장 위치는 다음 실행 때도 기억 |
| 기반 | 기존 AOI 도구 구조를 그대로 재사용: VBS 실행기 → 공용 venv → pywebview + WebView2. 추가 설치 패키지 없음 |
| 느린 네트워크 대응 | **"전부 읽고 시작"하지 않고 "앞뒤로 미리 읽기"**. 첫 사진만 준비되면 바로 시작하고, 현재 위치 앞 200장 / 뒤 50장을 8개 스레드가 병렬로 미리 읽어 RAM에 둠 |
| 사진 전달 | Python 내부 로컬 서버(127.0.0.1, 임의 포트, 세션 토큰)가 원본을 그대로 전달. 화면은 미리 디코딩해 둔 사진으로 교체만 함 |
| 연타 안정성 | 키 입력은 **화면(JS)에서 즉시·동기 처리**하고, 저장은 뒤에서 묶어서 처리. **Space는 지금 화면에 보이는 사진에만 적용**, Space 누르고 있기·연속 두 번 눌림 방지, 아직 안 뜬 사진으로는 넘어가지 않음 |
| 진행 보호 | GOOD 목록과 확인 위치를 1초마다 로컬에 자동 저장. 꺼져도 같은 폴더를 다시 열면 "이어하기" |
| 결과 | 미리 정한 위치에 `<폴더명>_GOOD.txt`, `<폴더명>_REJECT.txt` — 한 줄에 파일 이름 1개 |
| 목표 성능 | 키 입력 → 다음 사진 1프레임(≈16 ms) 이내, 초당 20회 연타에서도 누락·오적용 0건 |

## 1. 요구사항 정리

1. 폴더 안의 사진은 전부 **Reject 판정된 Defect 사진**이다.
2. 사람이 한 장씩 넘겨 보며 **GOOD 처리할 사진만 골라낸다**. 고르지 않은 사진은 REJECT로 남는다.
3. 폴더당 최대 1만 장, **네트워크 폴더**(`\\서버\공유\...`)라 사진 하나를 여는 데 시간이 걸린다.
4. 흐름: (사진 폴더 + 저장 위치 지정) → 사진 로딩 → `←`/`→`로 넘기며 `Space`로 GOOD 지정 → 결과 한 번 확인 → GOOD / REJECT 목록을 **사진 이름만** 텍스트 파일 2개로 저장
5. 속도가 최우선. 빠른 로딩, 그리고 키보드를 빠르게 연타해도 문제없이 동작해야 한다.

### 1-1. 결정이 필요한 항목 (제안 기본값으로 진행해도 되는지 확인 부탁드립니다)

| # | 항목 | 제안 기본값 | 대안 |
|---|---|---|---|
| Q1 | Space를 누른 뒤 동작 | **제자리에서 GOOD 지정/해제만** 하고, 넘기는 건 `→`로 (다시 Space를 누르면 해제) | Space = GOOD 지정 + 자동으로 다음 사진 |
| Q2 | 방향키를 누르고 있을 때 | **1번 누름 = 1장** (자동 반복 무시, 모든 사진을 한 번씩 확실히 보게 함) | 누르고 있으면 연속 넘김 (초당 10장 제한, 사진이 화면에 그려진 뒤에만 다음으로) |
| Q3 | 결과 파일 2개 | `<사진폴더명>_GOOD.txt`(Space로 고른 사진), `<사진폴더명>_REJECT.txt`(나머지 전부) | GOOD 목록 1개만 |
| Q4 | 결과 파일 형식 | 파일 이름 **확장자 포함**(`IMG_0001.jpg`), 폴더 정렬 순서, 줄바꿈 CRLF, **UTF-8** | 확장자 제외 / CP949(구형 프로그램 호환) |
| Q5 | 저장 위치에 같은 이름의 결과 파일이 이미 있을 때 | 덮어쓸지 묻기 | 항상 시각을 붙여 새 파일로 저장(`_GOOD_20261009_1530.txt`) |
| Q6 | 화면에 한 번도 표시되지 않은 사진이 남은 채로 저장 | 경고(미확인 N장, [미확인 사진 보기]) 후 허용. 해당 사진은 REJECT로 저장 | 전부 확인해야 저장 가능 |

지난 계획에서 따로 말씀이 없던 항목은 기본값을 그대로 유지합니다.
- 사진 형식: `.jpg .jpeg .png .bmp` (+ `.tif .tiff`는 변환해 표시)
- 범위: 선택한 폴더만 (하위 폴더 미포함)
- 프로그램 이름: `AOI Photo Sorter v1`

## 2. 전체 구조

```
AOI_Photo_Sorter_v1.vbs               (기존 실행기 템플릿 그대로, 빠른 경로 → pythonw app.py)
└─ app.py  (Python 1개 프로세스)
   ├─ 메인 스레드: pywebview / WebView2 창
   │     · 브리지(pywebview.api)는 "폴더 선택 창, 저장 위치 선택, 탐색기 열기" 같은 드문 호출만 사용
   ├─ 로컬 서버 스레드: 127.0.0.1:<임의 포트>/<세션 토큰>/
   │     · 화면(HTML), 원본 사진, GOOD 썸네일, 진행 상황 동기화 — 자주 오가는 데이터는 전부 여기로
   ├─ 미리 읽기 스레드 8개: 네트워크 폴더 → RAM (우선순위 = 현재 위치에서 가까운 순)
   └─ 자동 저장: GOOD 목록·확인 위치 변경분을 1초 단위로 로컬 세션 파일에 원자적 기록
```

### 2-1. 왜 이 구조인가

- **기존 도구와 같은 실행·설치 구조**: 검증된 VBS 빠른 실행 경로, 공용 venv, 영구 WebView2 프로필, 단일 실행 Mutex, 지연 import를 그대로 씁니다. 필요한 패키지(pywebview, pythonnet, Pillow)가 이미 공용 환경에 있어 추가 설치가 사실상 없습니다. `runtime.py` / `setup_env.py` / `constraints.txt`는 기존 두 프로그램과 **동일 파일**을 유지합니다.
- **사진을 pywebview 브리지로 보내지 않는 이유**: 브리지는 결과를 JSON 문자열로 만들어 WebView2 UI 스레드의 `ExecuteScript`로 넘깁니다. 사진 1장(수백 KB)을 base64(+33%)로 보내면 장당 수십 ms씩 UI 스레드가 막혀, 연타할 때 화면이 끊깁니다.
- **로컬 서버를 쓰는 이유와 안전장치**
  - 브라우저가 원본 바이트를 그대로 받아 **자체 디코더(화면 밖 스레드)**로 처리합니다. 가장 빠른 경로입니다.
  - 화면 HTML도 같은 서버에서 제공해 **같은 출처(same-origin)**로 만듭니다. 그래서 WebView2/Chromium의 로컬 네트워크 접근 제한이나 CORS 문제가 생기지 않습니다.
  - 포트는 OS가 빈 포트를 고르도록 0번으로 바인딩합니다. 예전 pywebview 고정 포트(42001)에서 생기던 충돌이 없고, 127.0.0.1에만 열리므로 방화벽 창도 뜨지 않습니다.
  - 주소에 실행할 때마다 바뀌는 **랜덤 토큰**을 넣습니다. 사진은 **번호로만** 요청하므로 임의 경로에 접근할 수 없습니다.
  - `Cache-Control: no-store`로 WebView2가 사진 수 GB를 디스크 캐시에 쌓지 않게 합니다.

## 3. 엔진 설계 (Python)

### 3-1. 폴더 스캔

- `os.scandir()` 1회로 목록을 읽습니다. Windows에서는 크기·수정 시각이 목록과 함께 오므로 **파일마다 추가 네트워크 왕복이 없습니다**. `Path.glob()` + 파일별 `stat()`은 1만 번 왕복하므로 쓰지 않습니다.
- 확장자로 거른 뒤 **탐색기와 같은 순서**로 정렬합니다(Windows `StrCmpLogicalW`: `IMG_2` → `IMG_10` 순).
- 스캔 중에는 "찾은 사진 N장"을 표시하고, 끝나면 바로 첫 사진을 준비합니다. 작업을 시작한 뒤 폴더에 새로 생긴 파일은 반영하지 않습니다.

### 3-2. 미리 읽기 (핵심)

1만 장을 모두 읽고 시작하면 4 GB(장당 400 KB 가정)를 다 읽을 때까지 수 분을 기다려야 하고 RAM도 부족합니다. 그래서 **현재 위치 기준으로 필요한 만큼만 앞뒤로 미리 읽습니다.** v2는 `←`로 되돌아가 다시 보는 경우가 많으므로 뒤쪽도 유지합니다.

```
           뒤쪽 유지(← 이동용)              현재            앞쪽 미리 읽기
  ... ─── [−50 ……… −1] ─────────────── [ 0 ] ─── [+1 +2 … +200] ─── ... 나머지는 아직 안 읽음
  우선순위:  3(−1~−5) / 5(나머지)           1         2(+1~+10) → 4(+11~+200)
```

- 스케줄러가 현재 위치를 기준으로 "있어야 할 사진 목록"을 계산하고, 가까운 순서(앞쪽 우선)로 읽기 스레드 8개에 나눠 줍니다. 위치가 바뀌면(넘기기, 되돌아가기, 확인 화면에서 이동) 즉시 다시 계산합니다.
- **병렬 읽기**: 네트워크 폴더에서는 파일 하나를 여는 지연(왕복 시간)이 병목입니다. 8개를 동시에 읽으면 그 지연이 겹쳐서 숨겨집니다. 예를 들어 파일당 50 ms인 느린 공유 폴더에서도 초당 약 160장을 읽어, 사람이 넘기는 속도(초당 2~10장)보다 훨씬 빠릅니다.
- 파일은 `open → read(전체) → close`로 한 번에 읽습니다.
- 읽기 실패(잠김, 일시적 끊김)는 0.2 s → 0.5 s → 1 s 간격으로 3회 재시도합니다. 그래도 실패하면 "읽기 실패" 카드를 띄웁니다(6장).
- 화면이 아직 준비되지 않은 사진을 요청하면 그 사진을 **맨 앞 순위로 올리고** 준비되는 즉시 응답합니다.

### 3-3. 메모리 관리

| 저장소 | 내용 | 한도(기본값) |
|---|---|---|
| RAM 원본 창 | 현재 위치 앞 200장 / 뒤 50장의 원본 바이트 | 384 MB + 128 MB(개수·용량 중 먼저 닿는 쪽). PC 메모리 8 GB 이하이면 절반으로 자동 축소 |
| GOOD 썸네일 | **GOOD으로 지정한 사진만**, 긴 변 192 px JPEG(약 8 KB) | 지정 시점에 RAM에 있는 원본으로 생성하므로 네트워크 재사용 없음 |
| 화면(JS) 디코딩 버퍼 | 다음 5장 / 이전 3장을 **화면 크기로 디코딩해 둔** ImageBitmap | 약 40~60 MB |

- 창 밖으로 나간 원본은 먼 것부터 버립니다. 1만 장을 끝까지 넘겨도 메모리는 일정하게 유지됩니다.
- 사진은 처음 지나갈 때 네트워크에서 **한 번만** 읽습니다. 다시 읽는 경우는 50장 넘게 되돌아가거나 확인 화면에서 오래전 사진을 크게 볼 때뿐입니다(장당 약 0.1초).
- 썸네일은 Pillow 축소 디코딩(`draft`)으로 장당 수 ms면 만듭니다. 이어하기로 썸네일이 없는 GOOD 사진은 확인 화면에서 보이는 것만 그때 만듭니다.

### 3-4. 사진 표시 원칙

- **원본 그대로 표시**합니다(재압축 없음). 판정용 사진이므로 화질 손실을 만들지 않습니다.
- 브라우저가 표시하지 못하는 형식(TIFF)만 Python에서 PNG로 변환합니다.
- 화면보다 큰 사진은 화면에 맞춰 고품질로 축소합니다. `F` 키로 100% 보기와 화면 맞춤을 전환하고, 휠로 확대·드래그로 이동합니다(확대할 때만 해당 1장의 원본을 다시 디코딩).

### 3-5. 상태 모델

| 상태 | 의미 | 저장 형태 |
|---|---|---|
| GOOD | Space로 지정한 사진 | 파일 이름 목록 |
| REJECT | 나머지 전부(기본값) | 저장하지 않음(전체 − GOOD) |
| 확인됨 | 한 번이라도 **실제로 화면에 그려진** 사진 | 1만 비트 문자열(약 10 KB) |

"확인됨"은 확인 화면의 **미확인 사진 경고**에 씁니다. 사진이 늦게 떠서 건너뛴 사진이 없는지 검증하는 용도입니다.

### 3-6. 진행 상황 자동 저장 / 이어하기

- 위치: `%LOCALAPPDATA%\AOI_Tools\Photo_Sorter\sessions\<폴더 경로 해시>.json`
- 내용: 사진 폴더, 결과 저장 위치, 파일 이름 목록, GOOD 목록, 확인됨 비트, 현재 위치, 시각
- 화면에서 바뀐 내용을 1초 단위로 묶어 Python에 보냅니다. 순번을 붙여 순서를 보장하고, 실패하면 재전송합니다. Python은 **임시 파일 → 교체(os.replace)**로 기록하므로 기록 중 꺼져도 파일이 깨지지 않고, 잃는 것은 최대 1초분입니다.
- 같은 폴더를 다시 열면 "이전 작업 3,210 / 10,000 확인, GOOD 23 — 이어하기 / 새로 시작"을 묻습니다. GOOD은 **파일 이름 기준**으로 맞춥니다. 그사이 추가된 사진은 미확인 REJECT가 되고, 삭제된 사진은 제외하며 개수를 안내합니다.

### 3-7. 결과 저장 위치(사전 설정)와 저장

- **시작 화면에서 결과 저장 위치를 지정해야 시작 버튼이 켜집니다.** 지난번 위치는 `%LOCALAPPDATA%\AOI_Tools\Photo_Sorter\settings.json`에 기억해 두었다가 자동으로 채웁니다.
- 시작할 때 저장 위치에 **실제로 임시 파일을 써 보고 지워서** 쓰기 가능 여부를 확인합니다. 1시간 작업한 뒤에야 권한 오류를 발견하는 일을 막기 위해서입니다. 같은 이름의 결과 파일이 이미 있으면 이때 미리 알려 줍니다(Q5).
- 저장 파일: `<사진폴더명>_GOOD.txt`, `<사진폴더명>_REJECT.txt`. 한 줄에 파일 이름 1개, 폴더 정렬 순서이며 형식은 Q4를 따릅니다.
- 임시 파일에 쓴 뒤 교체하므로, 네트워크가 끊겨도 반쯤 쓰인 결과 파일이 남지 않습니다.
- 저장이 끝나면 두 파일 경로와 개수를 보여 주고 [폴더 열기]를 제공합니다.

### 4-2. 화면 구성

**1. 시작**: 두 경로를 모두 정해야 시작할 수 있습니다.
```
 AOI Photo Sorter v1
 ─────────────────────────────────────────────────────────────
  ① 사진 폴더      [ \\server\aoi\LOT123              ] [찾아보기]
  ② 결과 저장 위치 [ D:\AOI_결과                      ] [찾아보기]  ✓ 쓰기 가능

   \\server\aoi\LOT122   저장 완료 · GOOD 112
```
- UNC 경로는 붙여넣기가 빠르므로 경로 입력란과 [찾아보기]를 함께 둡니다.

**3. 선별 (주 화면)**: 사진 영역을 최대로 하고, 정보는 위·아래 한 줄씩만 둡니다.
```
 LOT123   1,234 / 10,000 (12.3%)   GOOD 23                  저장: D:\AOI_결과   미리 읽기 ●
 ████████░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░░
 ┌──────────────────────────────────────────────────────────────────────────────────────┐
 │ GOOD ✓                                                                               │ ← GOOD일 때만: 초록 테두리 + 표시
 │                              (  사 진  — 화면에 맞춤  )                                │
 │                                                                                      │
 └──────────────────────────────────────────────────────────────────────────────────────┘
 IMG_001234.jpg   [REJECT]                                 직전: IMG_001230.jpg → GOOD 지정
 ← 이전   → 다음   Space GOOD 지정/해제   F 확대   End 작업 위치   Esc 메뉴
```
- **GOOD 상태는 계속 보이게** 합니다(초록 테두리, 왼쪽 위 `GOOD ✓`, 아래쪽 `[GOOD]`/`[REJECT]`). ←로 돌아왔을 때도 상태를 바로 알 수 있습니다.
- Space를 누르면 0.15초간 강조 효과가 나서 입력이 들어갔다는 것을 알려 줍니다. 효과는 투명도만 바꾸므로 화면 배치 계산이 일어나지 않습니다.
- "직전: … → GOOD 지정/해제"는 방금 한 동작을 확인하는 용도입니다.
- 진행 막대는 확인 진행률입니다. 오른쪽 점(●)은 미리 읽기 상태입니다(초록: 충분 / 노랑: 따라잡히는 중 / 빨강: 네트워크 대기).
- 마지막 사진에서 `→`를 누르면 "마지막 사진입니다. Enter: 확인 화면으로"를 띄웁니다.

**4. 확인**: GOOD 목록(보통 수가 적음)을 한눈에 확인합니다.
```
 확인   전체 10,000   GOOD 23   REJECT 9,977   미확인 0
 GOOD 목록 (23)                                          [ GOOD만 다시 넘겨보기 ]
 ┌────┐┌────┐┌────┐┌────┐┌────┐┌────┐┌────┐┌────┐
 │    ││    ││ ▣  ││    ││    ││    ││    ││    │   ← 썸네일 (보이는 부분만 그림)
 └────┘└────┘└────┘└────┘└────┘└────┘└────┘└────┘
  클릭 / Space: GOOD 해제(→REJECT)   Enter: 크게 보기   방향키: 이동
  저장 위치: D:\AOI_결과  →  LOT123_GOOD.txt (23), LOT123_REJECT.txt (9,977)     [ 저장 (Ctrl+S) ]
```

- **GOOD만 다시 넘겨보기**: GOOD 사진만 선별 화면과 같은 방식으로 다시 넘기며, Space로 해제할 수 있습니다.
- 미확인 사진이 있으면 "미확인 120장 — 저장하면 REJECT로 들어갑니다 [미확인 사진 보기]"를 강조해 표시합니다. [미확인 사진 보기]를 누르면 미확인 사진만 이어서 넘겨 볼 수 있습니다.

**5. 완료**: 저장한 두 파일의 경로·개수, [폴더 열기], [새 작업]

### 4-3. 키 배치

| 화면 | 키 | 동작 |
|---|---|---|
| 선별 | `→` | 다음 사진 |
| 선별 | `←` | 이전 사진 |
| 선별 | `Space` | 지금 보이는 사진 GOOD 지정 ↔ 해제 (Q1: 제자리 토글) |
| 선별 | `End` / `Home` | 작업 위치(처음 보는 사진) / 첫 사진 |
| 선별 | `F`, 휠, 드래그 | 100% 보기 / 화면 맞춤, 확대, 이동 |
| 선별 | `Enter` (마지막 사진에서) | 확인 화면으로 |
| 선별 | `Esc` | 메뉴 (확인 화면으로, 처음으로) |
| 확인 | `Ctrl+S` | 미리 정한 위치에 결과 저장 |

### 4-4. 빠른 연타 안정성 규칙 (핵심)

1. **입력은 화면(JS)에서 즉시·동기 처리합니다.** 키 1번에 상태 변경 1번이며, Python 응답을 기다리지 않습니다. 키 이벤트는 단일 스레드 이벤트 루프에서 들어온 순서대로 처리되므로 순서가 뒤바뀌지 않습니다.
2. **Space는 지금 화면에 그려져 있는 사진에만 적용됩니다.** 다음 사진으로 넘어가는 중이라 아직 화면에 그려지지 않았다면 그 Space는 무시합니다. 보지 않은 사진이 GOOD이 되는 일이 생기지 않습니다.
3. **화면에 뜨지 않은 사진을 건너뛰지 않습니다.** 다음 사진이 준비 전이면 `→`는 그 사진으로 이동해 "불러오는 중"을 표시하고, 사진이 화면에 뜰 때까지 이후의 `→`와 Space는 무시합니다. 입력을 쌓아 두었다가 나중에 한꺼번에 넘기지 않습니다. 그래서 모든 사진은 지나갈 때 반드시 한 번 화면에 그려지고, 그려진 사진만 "확인됨"으로 기록됩니다. 되돌아가는 `←`, `Home`, `End`는 건너뛰는 사진이 생기지 않으므로 로딩 중에도 동작합니다.
4. **Space를 누르고 있어도 한 번만 처리합니다** (자동 반복 무시, 고정). 누르고 있다고 GOOD이 켜졌다 꺼졌다 반복되지 않습니다. 같은 사진에서 150 ms 안에 Space가 한 번 더 들어오면(키가 튀어 두 번 눌린 경우) 무시합니다.
5. **방향키를 누르고 있을 때**는 Q2 결정에 따릅니다. 기본은 1번 누름 = 1장입니다.
6. **Space가 엉뚱하게 동작하지 않게 막습니다.** 브라우저 기본 동작(페이지 스크롤, 포커스된 버튼 클릭)을 모두 차단합니다. 버튼은 키보드 포커스를 받지 않고, 다른 창에 갔다 와도 포커스를 자동으로 복구합니다. 키는 글자 값이 아니라 물리 키(`event.code`)로 읽으므로 한/영·CapsLock 영향이 없습니다.
7. **다음 사진은 미리 디코딩해 둔 것으로 교체만 합니다.** 화면 크기로 디코딩한 ImageBitmap을 캔버스에 그리기만 하므로 1프레임 안에 끝나고, 숫자 표시는 프레임당 1번만 갱신합니다.
8. **저장은 화면을 막지 않습니다.** 변경분을 묶어 비동기로 보내고, 순번으로 순서를 보장하며, 실패하면 재전송합니다.

| 네트워크 폴더가 매우 느린 경우 | 설정에서 읽기 스레드를 늘림. 필요하면 "시작 전 로컬로 전체 복사" 옵션 추가 가능(디스크 사용량이 크므로 기본은 끔) |
| Windows 실기 미검증 | Linux에서 같은 엔진(Chromium)으로 E2E 검증. 최종 체감 확인은 실기에서 요청 |

## 11. v2 변경 (v1 사용 피드백)

| 항목 | v1 | v2 |
|---|---|---|
| `Space` | 지금 사진 GOOD 지정/해제(제자리) | GOOD 지정(이미 GOOD이면 해제) + **다음 사진으로 이동**. 마지막 사진에서는 지정만 하고 머묾 |
| GOOD 표시 | 화면 전체 반짝임(0.16초) + 초록 테두리 6px + 큰 배지 | **작은 정적 배지 + 하단 상태 글자만**. 반짝임·테두리 제거 |
| 정보 줄 갱신 | 매 프레임 모든 값 다시 쓰기 | 바뀐 값만 쓰기, 상단·하단 줄은 `contain: strict`로 배치 계산 범위 제한 |
| 두 번 눌림 보호 | 같은 사진에서 150 ms 안의 두 번째 Space 무시(`space_debounce_ms`) | 사진이 화면에 뜬 지 120 ms가 안 된 Space 무시(`space_min_view_ms`). Space가 사진을 넘기므로, 튄 두 번째 입력이 방금 뜬 다음 사진을 GOOD으로 만드는 일을 막음 |
| 확인 화면 `Space` | 선택 칸 GOOD ↔ 해제 | 해제/지정 + 다음 칸 선택 |

측정(같은 모의 환경): `Space` → 다음 사진 프레임 p50 24 ms / p95 37 ms(80회), 초당 20회 `→` + 4장마다 GOOD 300회 입력에서 무시된 입력 0건.

## 12. v3: 네트워크 폴더 연결 끊김 대응

v2까지는 끊긴 동안 실패한 사진이 "읽기 실패"로 고정되어, 연결이 돌아와도 사진마다 `R`을 눌러야 했습니다(모의 시험: 재연결 뒤 20장 모두 실패 유지).

| 구성 | 동작 |
|---|---|
| 끊김 판정 (`engine.ImageCache`) | 사진 읽기가 재시도까지 실패하면 사진 폴더 자체를 확인(`os.stat`). 폴더도 안 되면 **offline**(그 사진은 실패로 기록하지 않음), 폴더가 되면 그 파일만의 실패로 기록 |
| offline 동안 | 미리 읽기 중단(끊긴 공유 폴더에 읽기를 계속 시도하지 않음), 메모리에 없는 사진 요청은 즉시 `offline` 응답(60초 대기 없음), 감시 스레드가 2초마다 폴더 확인 |
| 복구 | 폴더가 다시 응답하면 실패 기록을 모두 지우고 `epoch` +1 → 미리 읽기 재개 |
| F5 새로고침 (`api/refresh`) | offline 상태와 실패 기록을 즉시 지우고 `epoch` +1. 여전히 끊겨 있으면 곧 다시 offline이 됨 |
| 응답 없음 | 5초 넘게 끝나지 않는 읽기가 있으면 `stalled` |
| 화면 | 1초마다 받는 상태(`offline`, `stalled`, `epoch`)로 위쪽 안내 표시, `epoch`가 바뀌면 실패한 사진·썸네일을 다시 불러옴. 사진 응답의 `X-Photo-Error: offline/read`로 카드 문구 구분. `F5`/`R`/`Ctrl+R`/메뉴 = 새로고침(페이지 다시 읽기는 하지 않음) |

측정(모의): 끊김 → 첫 미독 사진 "연결 끊김" 카드 2.0초, 복구 → 키 입력 없이 사진 재표시 2.7초, 확인 화면 썸네일 재표시 2.0초, 파일 실패 → F5로 즉시 복구, 응답 없음 안내 표시 후 해제 확인. E2E: `test_network_outage_recovers_by_itself`, `test_refresh_key_reloads_failed_photos`, `test_forward_waits_for_a_loading_photo`(응답 대기 안내).
